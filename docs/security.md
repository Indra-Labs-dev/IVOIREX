# Security

Les mots de passe sont hachés, jamais renvoyés dans les réponses. Les JWT HS256 acceptent uniquement l’algorithme explicite, ont une expiration et séparent le type d’usage. Un limiteur fixe par fenêtre Redis protège register, login et refresh (5/10/20 requêtes par minute et adresse). L’API n’accepte `X-Forwarded-For` que depuis l’adresse privée frontend fixée dans Compose; les autres pairs sont limités par leur adresse réseau directe. Le BFF ne relaie cet en-tête que si `TRUST_CLIENT_IP_HEADERS=true`; ne l’activer que si le proxy public remplace l’en-tête à partir de l’adresse réellement observée. Redis indisponible fait échouer ces mutations en 503. Le secret provient de l’environnement ; en mode production, un secret de moins de 32 caractères fait échouer la configuration. CORS autorise uniquement les origines configurées et les méthodes HTTP utiles. SQLAlchemy utilise des paramètres liés ; les entrées HTTP sont validées par Pydantic.

L’interface web utilise un route handler de même origine, des cookies `HttpOnly` et `SameSite=Lax`, `Secure` en production, avec vérification d’origine pour les mutations. Les jetons ne sont pas exposés au JavaScript client. L’API conserve aussi son accès Bearer pour les intégrations directes.

Restent à concevoir avant production : rotation et révocation individuelle des refresh tokens, RBAC appliqué aux ressources, audit log, politique de sécurité des headers/CSP, protection CSRF dédiée si la politique d’origine change, détection brute force et observabilité. Les valeurs `.env.example` sont locales uniquement.
